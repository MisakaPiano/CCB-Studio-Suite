# 新工作台备份与恢复流程

任务 UX_RECOVERY_CONTINUOUS / C03；基线 `684401040b96f921eae9066fc4912324a768b824`，分支 `feature/windows-rc-continuous`。PRODUCT_HOLD / NOT RC。

追踪表复核发现：已有 StudioWorkspace.backup / StudioRestore / 格式复制迁移实际消费者只在旧 Preview 和测试，新工作台缺少用户入口。这是产品接线缺口，不重新实现资产安全核心。

资产管理新增“备份与恢复”。当前草稿保存后调用原备份核心，显示完整目录、打开文件夹与复制路径；备份包含不可变资产、工程、独立 Prompt、标签、历史和账户引用，排除实际凭据、本机目录授权、缓存和旧导出。用户选择完整备份及存放位置，先确认新目录与凭据限制，再完整校验并恢复；不覆盖当前或已有目录。旧格式保留原恢复目录，另建格式 3 副本；新副本通过目录和资产管理记录校验后出现“打开恢复工作区”。安装版启动同一个应用的独立窗口并传递明确工作区/运行目录，当前窗口不关闭；启动请求本身不冒充目标窗口启动成功。

恢复失败清楚显示未完成，旧资料、备份和暂存副本保留。资产管理记录异常时仍可访问备份恢复页；不把管理异常视作可重置图库的许可。

验证使用合成数据，真实 API 0：

- 通过实际新工作台 Compose 导航→创建备份→取消恢复→确认恢复→打开工作区回调，再用实际存储实现打开新目录，核对原件字节、整册工程、独立 Prompt、别名标签、未发送草稿和缺凭据状态。原工作区凭据仍可用；恢复目录自动收集为空。
- 当前根内部恢复位置被拒绝；已有目标目录及哨兵文件保持不变；未知备份内容拒绝且目标不发布。
- 旧 Preview 备份恢复后复制转换为当前格式，旧恢复目录和备份清单不变。

三项定向实际 PASS。首轮测试编译错误（工程引用与文档类型混用）、随后 JUnit 返回类型初始化失败均保留；不能把它们写成已执行产品用例 PASS。完整桌面回归 90 项实际 PASS，219.858 秒，0 failures/errors/skipped，sourceStable=true；原始日志、JUnit XML、源码身份及离屏截图位于 [证据目录](evidence/UX_LIBRARY_BACKUP)。

环境沿用 JDK Temurin 17.0.20.1 / Gradle 9.1.0；离线、严格依赖校验、单 worker，测试 JVM 256 MiB / 2 CPU。资产核心没有改动；本轮不重跑其全量历史测试。

文件选择器和启动独立窗口的 OS 边界在 GUI 回归中注入可控实现；原生文件选择、已安装程序第二窗口启动和用户体验仍需固定包验证。离屏截图及测试通过不代表集中真人验收通过。继续 C03 安装版路径、动作映射与剩余 W1–W5/更新门槛。
